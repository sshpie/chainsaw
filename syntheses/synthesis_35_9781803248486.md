## One-liner

A beginner-friendly, hands-on walkthrough of penetration testing the three dominant cloud platforms (AWS, Azure, GCP), built around free-tier lab deployments, first-party security tools, and a curated set of open-source scanners run from each provider's own Cloud Shell.

## Thesis

Cloud pentesting is fundamentally different from on-premises pentesting because Amazon, Microsoft, and Google own the infrastructure, which means the provider's rules of engagement legally override the client's wishes; the shared responsibility model ("the provider secures the cloud, your organization secures what is in the cloud") defines where the pentester's scope actually lives, and the practitioner's real job is to find how an attacker could harm a client's cloud before a real attacker does, then communicate it in a report that makes executives feel the dollar risk. Crawley argues the skills are learnable by anyone with an ordinary PC, a browser, and a reliable internet connection, because the cloud does the heavy compute and most modern tooling runs from the provider's own CLI.

## Core ideas

1. The shared responsibility model is the organizing principle of the whole book: the cloud provider is responsible for security OF the cloud (physical data centers, hardware, networking, its own code) and your organization is responsible for security IN the cloud (your code, your traffic, your configurations). The mnemonic is stated verbatim and the IaaS/PaaS/SaaS gradient is explained as 'how much of the code is yours versus the provider's' (SaaS = Gmail, the provider owns most; PaaS = Amazon EKS; IaaS = Azure VMs, you own the OS).
2. The provider's rules of engagement legally trump the client's wishes, because you are testing on Amazon, Microsoft, and Google's infrastructure. Crawley repeatedly cites the AWS penetration testing policy, the Microsoft Cloud Penetration Testing Rules of Engagement, and the GCP Acceptable Use Policy, and stresses you must never do anything in a contract that those policies forbid.
3. DDoS/DoS simulation is almost always forbidden, with one documented exception: AWS permits DDoS simulation testing under its specific policy only if bit volume stays under 20 Gbps and packet volume stays under 5 million packets/sec against CloudFront (or 50,000 pps against other resources), it does not originate from another AWS resource, and AWS can order you to stop at any time. Her advice: if you are even slightly unsure it is permitted, do not do it.
4. Vulnerability prioritization should be driven by EPSS first, then CVSS, not CVSS alone. A vuln with CVSS 9.5 but EPSS 5% can rank below a CVSS 5.7 vuln with EPSS 95%, because EPSS estimates real-world exploitation probability. CVSS bands are spelled out (0.1-3.9 low, 4.0-6.9 medium, 7.0-8.9 high, 9.0-10.0 critical) and CVE records (CVE-YYYY-NNNN, maintained by MITRE) are her working definition of a 'known vulnerability.'
5. Cloud attacks are categorized as external versus internal, and internal attacks (malicious insiders, contractors, supply-chain entities who are already inside) are framed as easier to execute and often more destructive because they skip the break-in and proceed via privilege escalation and lateral movement. Lateral movement is taught through six specific MITRE techniques: exploitation of remote services, internal spearphishing, lateral tool transfer, remote service session hijacking, software deployment tools, and tainted shared content.
6. Zero-trust replaces the obsolete 1990s perimeter model. In zero-trust no machine, device, or user is automatically trusted regardless of origin, and every possible authentication point re-authenticates, whereas the perimeter model trusted everything inside the wall. Crawley argues only zero-trust actually works in the cloud and that it is the only model that meaningfully detects internal attacks.
7. A pentest is legally distinguished from a real cyberattack solely by the written, mutually signed consent of the system owner; a verbal or 'gentleman's agreement' will not hold up in court, and acting without a signed contract is digital crime in most countries. The contract must define a specific scope (IP addresses, network segments, domains) that you never exceed, even if you think exceeding it serves the client.
8. The pentest report is the deliverable that makes all the work matter, and it must be written for executives who care about money. She recommends citing IBM's Cost of a Data Breach Report in the executive summary, and prescribes a fixed section structure (executive summary, scope, vulnerability findings ordered by EPSS then CVSS, other/additional findings, remediation advice, conclusion, references), noting ~50 pages is a typical length but length should follow the findings.
9. Containerization is taught as virtualization that ships only the components needed to run the code, contrasted with VMs that virtualize a whole OS. Docker (host, daemon, images, registry, client) is the foundation and Kubernetes is described as 'a fork of Docker, like Ubuntu to Debian,' with a full control-plane breakdown (etcd, kube-scheduler, kube-apiserver, kube-controller-manager, cloud-controller-manager) over nodes (kubelets) and Pods, and the load balancer and API servers called out as the two primary attack vectors (north-south ingress vs east-west).
10. Each cloud provider has a first-party security stack the pentester should leverage as a starting point: AWS Security Hub aggregates IAM, Macie, Inspector, GuardDuty, Firewall Manager, and Config; Azure centers on Microsoft Defender for Cloud and Sentinel; GCP centers on Security Command Center (which may require a Google Workspace or Cloud Identity account). These native tools can themselves surface exposed services and CVE/CVSS-tagged findings usable in a report.
11. Hands-on practice is non-negotiable and entirely free-tier achievable: the book is built around spinning up your own AWS, Azure, and GCP deployments (a GCP Compute Engine VM named 'crowgirl-1', a Cloud Run Docker service 'crawleydockertest', a GKE 'hello-cluster'), running tools from the provider's Cloud Shell, and being reminded to watch billing so you incur no charges.
12. The auth-and-misconfiguration reality is demonstrated concretely: even a minimal GCP lab with almost nothing on it, GCPBucketBrute still found a publicly listable and readable bucket ('pictures-test') with unauthenticated storage.objects.list and storage.objects.get, and a default Cloud Run Docker image scanned by Trivy came back 'very misconfigured.' Misconfigurations are repeatedly defined as exploitable security vulnerabilities.

## Techniques and methods

- Set up free-tier lab environments in all three clouds and drive them from the provider's browser-based Cloud Shell, treating the laptop as a thin client (the book explicitly notes you only need a quad-core 64-bit CPU and 4 GB RAM because the cloud does the compute).
- Run Prowler as the universal cross-cloud compliance/vulnerability scanner: 'prowler aws', 'prowler azure', 'prowler gcp', with -h to enumerate services/checks, and output to CSV/JSON/HTML for the report. Prowler is called possibly the most essential third-party tool in the book.
- Use Pacu (Rhino Security Labs) as an AWS exploitation framework with modules (not just a scanner) to enumerate exposed services, plus Cred Scanner for exposed keys/secrets in files, CloudFrunt for misconfigured CloudFront domains, and Redboto/WeirdAAL/awspx/Buckethead for further AWS recon.
- Azure-specific tooling: MicroBurst and PowerZure for offensive Azure operations, ScoutSuite for multi-cloud auditing, SkyArk for privilege discovery, BlobHunter/CloudBrute for storage, and MFASweep (dafthack) to verify whether MFA is actually enabled across Microsoft 365/Azure surfaces.
- GCP-specific tooling: GCPBucketBrute for unauthenticated Google Storage bucket enumeration and privilege-escalation checks (python3 gcpbucketbrute.py -k <keyword> -u), and GCP Scanner (a Google-maintained but unofficial tool) to determine what access a set of credentials has, including a metadata scan (scanner.py -o <dir> -ls -m) for credentials exposed in GCE instance metadata.
- Container pentesting workflow: deploy Docker via Cloud Run / ECS / ACI and Kubernetes via GKE / EKS / AKS, expose the deployment through a LoadBalancer (kubectl expose deployment ... --type LoadBalancer --port 80 --target-port 8080), inspect with kubectl get pods / get service, then scan.
- Scan containers with Trivy (Aqua Security): 'trivy image --image-config-scanners config <image>' to find Docker image misconfigurations, and 'trivy k8s -n kube-system --report summary all --timeout 1500s' for a thorough Kubernetes cluster report; supplement with kube-bench (CIS Kubernetes Benchmark), kube-hunter, kdigger, and Vishnunair's Parrot-OS-based automated-pentest Docker image.
- Vulnerability triage method for the report: look up unknown CVSS/EPSS from CVEDetails.com, sort findings by EPSS rating first then CVSS score, write each vuln's exploitability in your own words, and separate CVE-mapped findings from non-CVE 'Other Findings' (e.g., accounts lacking MFA).
- Map observed attacker behavior to MITRE ATT&CK techniques (drive-by compromise, exploit public-facing application, external remote services, valid/cloud accounts, the six lateral-movement techniques, data from cloud storage) using the ATT&CK and CVE databases as primary references.
- Lean on first-party scanning before/alongside third-party tools: AWS Security Hub and Amazon Inspector (CVE/CVSS-tagged scans, exposed-service detection), Azure Microsoft Defender for Cloud, and GCP Security Command Center as the integrated starting point for each platform.
- Operational discipline: always obtain a signed contract with a specific scope before any activity (even a vulnerability scan), review the AWS/Microsoft/Google pentesting policies before each engagement, watch provider billing to stay in free tier, and use a VPN on any public Wi-Fi.

## Memorable

- The shared responsibility mnemonic stated flat: 'the cloud provider is responsible for the security of the cloud and your organization is responsible for security in the cloud.' She drives it home: even if your company spends $100,000/month on AWS, Amazon will not let you inside one of its data centers.
- The lateral-movement-in-a-department-store image: an attacker entering through ingress and moving east-west is 'like a burglar breaking into a department store's jewelry department and then moving on to the fragrances and cosmetics.'
- The VM metaphor: a VM is your 'computer's pet computer,' and she runs a 64 GB-RAM laptop because each simulated machine could want 4 GB.
- The Kubernetes lineage line: 'Docker and Kubernetes aren't competitors like Coca-Cola and Pepsi. Rather, Kubernetes is kind of a fork of Docker, like comparing Debian Linux to Ubuntu Linux.' Kubernetes was announced by Google's Eric Brewer in 2014, inspired by the in-house Borg system that runs Gmail, Search, and Maps, and open-sourced by July 2015.
- The concrete lab proof: scanning a near-empty GCP deployment, GCPBucketBrute still returned 'UNAUTHENTICATED ACCESS ALLOWED: pictures-test' with storage.objects.list and storage.objects.get, prompting her surprise that even a bare VM exposed an open bucket.
- The AWS DDoS exception numbers: simulation allowed only under 20 Gbps and under 5 million packets/sec for CloudFront (50,000 pps for other resources), not from another AWS resource, terminable by AWS at any time, otherwise 'just don't try it in the first place. It's not worth it.'
- The EPSS-over-CVSS rule: 'A vulnerability may have a CVSS score of 9.5, but if its EPSS score is 5%, it may be a lower priority... than a vulnerability with a CVSS score of 5.7 but an EPSS score of 95%.'
- Executive-summary coaching with sample sentences: 'The cryptographic keys are stored well, but too many accounts with privileged access lack multi-factor authentication...' and the bottom line that 'Money is what motivates corporate executives,' with IBM's Cost of a Data Breach Report as the figure to cite.
- Real named lab artifacts the reader builds: a GCP Compute Engine VM 'crowgirl-1', a Cloud Run Docker service 'crawleydockertest', a GKE 'hello-cluster', and a sample project ID 'blissful-axiom-115916.'
- The contract warning: a pentest differs from a real attack only by 'full legal consent,' and a 'gentleman's agreement signed with a handshake' will not hold up in court; even a simple vulnerability scan without signed mutual consent 'can get you into a lot of trouble.' She points readers to Cure53's contract templates and PentestUSA's sample.
- Author voice details: Crawley cites her own SANS PenTest HackFest 2021 talk 'Writing Reports: The Overlooked Pen Testing Skill,' references the SCYTHE Purple Team Exercise Framework and Daniel Miessler, and notes ~50 pages is a typical report length though length should follow the findings.
- The closing reassurance and the book's democratizing thesis: 'The tools you need for your work are an ordinary PC, an updated web browser, and a good reliable internet connection... Isn't the internet wonderful?'

## Curriculum fit

Strong fit as an introductory, practice-first module in a cloud security or offensive security curriculum, positioned after networking fundamentals and a general pentesting primer. Its differentiators for a curriculum are: (1) genuinely tri-cloud coverage (AWS, Azure, GCP) with parallel chapter structure that lets an instructor teach one concept three ways; (2) every concept is paired with a free-tier, copy-pasteable lab and a Code in Action video, so it works as a lab manual; (3) it correctly foregrounds legal/scope/contract discipline and provider rules of engagement, which most tool-focused courses underweight; and (4) it teaches modern triage (EPSS before CVSS) and report-writing as a first-class deliverable. It maps cleanly to certification prep for CompTIA PenTest+, CCSK/CCSP, and the cloud-specialty AWS/Azure/Google security tracks the book itself recommends. Caveats for course designers: it is beginner-oriented and breadth-over-depth (it explicitly says you do not need to write YAML/JSON or build tools), the specific tool versions and provider console UIs will date quickly (Trivy v0.44.1, specific console click-paths), and it deliberately avoids deep exploit development, IAM privilege-escalation chaining, and adversary emulation depth, so it should be supplemented with hands-on cloud CTF/lab platforms and a follow-on advanced cloud red-team course. Best used as the on-ramp text, not the capstone.
