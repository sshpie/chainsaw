## One-liner

A hands-on apprenticeship that takes a reader from "Day Zero" (no target, no bug) to a coordinated zero-day disclosure, by drilling the three core disciplines of modern vulnerability research, code review, reverse engineering, and fuzzing, against real open-source and commercial software.

## Thesis

Finding zero-day vulnerabilities is not luck or innate talent; it is a teachable, repeatable craft built on three complementary disciplines that feed one another. The researcher's job is to model where attacker-controlled input enters a program (sources), where it reaches something dangerous (sinks), and to prove a path between the two. Code review reasons about that path from source code; reverse engineering recovers it when there is no source; fuzzing discovers it by brute mechanical exploration when manual reasoning runs out. None of the three is sufficient alone, and a skilled researcher fluidly switches among them, using coverage and instrumentation to turn a black box into a gray box. The work begins with disciplined target selection (familiarity, availability, impact) and does not end at a crash: a finding only matters once exploitability is confirmed, root cause is understood, variants are hunted across the rest of the codebase, and the whole thing is reported through coordinated disclosure so the vendor can fix it. The closing argument is that vulnerability research is ultimately a defensive act, a way to secure organizations and the software ecosystem, not just collect trophies.

## Core ideas

1. The source-to-sink mental model is the spine of the whole book: a vulnerability is a reachable, attacker-influenced path from a source (where untrusted input enters) to a sink (a dangerous operation). Every technique in the book is a different way to find or prove that path.
2. The three disciplines are complementary lenses on the same path, not rival schools. Code review reads the path from source; reverse engineering reconstructs it without source; fuzzing finds it by mechanical exploration. Mastery is knowing which to reach for and how to hand off between them.
3. Bugs are not vulnerabilities. A crash or a logic flaw becomes a vulnerability only when it is reachable from an attacker-controlled source and has security impact, which is why "confirming exploitability" is treated as a first-class step, not an afterthought.
4. Vulnerability research is distinct from penetration testing: a pentest assesses a deployed system against a deadline; vulnerability research goes deep on a single product to discover previously unknown flaws, with different goals, tempo, and deliverables.
5. Target selection is a deliberate triage, not a whim. The Familiarity / Availability / Impact heuristic steers a researcher toward targets they can understand, can actually obtain and run, and where a finding would matter, which is the difference between productive months and wasted ones.
6. One bug implies many: variant analysis is where the leverage is. Once you understand a flaw's root cause, you encode the pattern (with CodeQL or Semgrep over abstract syntax trees) and sweep it across the rest of the codebase, and across thousands of other repositories, to find every sibling of the same mistake.
7. Attack surface is mapped, not assumed. The book teaches a taxonomy of surfaces (web client, web server and nontraditional web endpoints, network protocols, and local surfaces like sockets, named pipes, symlinks, and IPC) and uses technical standards documents as a map of where input is parsed.
8. Without source you build a gray box. Code coverage, dynamic instrumentation (Frida), emulation (Qiling, Unicorn), and symbolic execution progressively recover the visibility that source code would have given, so reverse engineering and fuzzing can be steered rather than blind.
9. Coverage is the currency of fuzzing. Coverage-guided fuzzing (AFL++) beats dumb fuzzing because it keeps inputs that reach new code; the practical art is corpus minimization, writing harnesses, and clearing "fuzz blockers" such as checksums and validation gates that wall off deeper code.
10. A good fuzzer is described by a few axes: how much target information it uses (black, gray, white box), whether it generates or mutates inputs, the input type, and the feedback loop. Choosing a fuzzer is choosing positions on those axes for the target at hand.
11. The work is unfinished until it is reported. A vulnerability report (clear summary, deterministic reproduction steps, root-cause analysis, and concrete remediation) and coordinated disclosure through the right CNA or the Zero Day Initiative are presented as core skills, not paperwork.
12. Vulnerability research is a defensive discipline. The closing chapter reframes the entire offensive toolkit as a way to secure organizations: integrating research into the software development life cycle, prioritizing by real exploitability, and improving the ecosystem rather than hoarding bugs.

## Techniques and methods

- Sink-to-source taint analysis: start at a dangerous function, work backward to see whether attacker-controlled input can reach it, filter for genuinely exploitable scenarios, then build a minimal proof of concept.
- Automated variant analysis: model a known bug as a query over a program's abstract syntax tree, run it with CodeQL or Semgrep across one repository, then scale the same pattern across many repositories to find recurring instances of the bug class.
- Attack-surface mapping driven by standards and architecture: enumerate web, network-protocol, and local surfaces, read the relevant technical specifications as a guide to parsers and trust boundaries, and reason about local privilege-escalation surfaces.
- Binary triage by type: identify whether a target is an Electron or Python-packaged app, a managed .NET or Java binary, or native machine code, and whether it is statically or dynamically linked, stripped, or packed, because each class demands a different unpacking and analysis path.
- Static plus dynamic reverse engineering: disassemble and decompile in Ghidra and dump strings for static leads, then trace library and system calls, hook functions with Frida, and use canary strings to confirm which inputs reach which code at runtime.
- Hybrid analysis to steer the work: collect and visualize code coverage, emulate firmware and isolated functions with Qiling and Unicorn (including hijacking API calls and binding virtual paths), and apply symbolic execution with custom SimProcedures to solve input constraints.
- A graded fuzzing toolkit: black-box protocol fuzzing with boofuzz, zero-setup mutation fuzzing with radamsa, binary-template fuzzing with FormatFuzzer and 010 Editor templates, and crash triage with sanitizers such as AddressSanitizer.
- Coverage-guided fuzzing in depth with AFL++: corpus minimization, harness writing, diagnosing and removing fuzz blockers, and patching validation checks so the fuzzer can reach guarded code.
- Language- and grammar-aware fuzzing: Jazzer for Java, native Go fuzzing, and dictionary- and grammar-based fuzzing for structured text formats, plus leveraging OSS-Fuzz infrastructure.
- Disclosure craft: structuring a vulnerability report (summary, reproduction, root cause, recommendations) and running coordinated disclosure through CVEs, CNAs, and the Zero Day Initiative.

## Memorable

- The title is the whole pedagogy: "Day Zero" is the moment you have no target and no bug; the book walks the arc to a real zero-day and then "Beyond Day Zero" to disclosure, so the chapter numbering literally starts at 0.
- The author, Eugene "Spaceraccoon" Lim, was selected from a pool of one million white-hat hackers for HackerOne's 2021 H1-Elite Hall of Fame and has been credited with hundreds of disclosures from Amazon to Zoom, lending the techniques the weight of someone who actually ships findings.
- Targets are real, named, and current rather than toy examples: SONiC (the open-source network operating system), ImageMagick, libxls, the Expat XML parser, NanoMQ and the MQTT protocol, DbGate, and WeasyPrint, so every technique is shown landing on software people actually run.
- The Expat integer-overflow thread is the variant-analysis showpiece: one root cause is generalized into a pattern and then matched across the codebase to surface a family of related bugs, the book's argument that "one bug means many" made concrete.
- The book is openly a standing-on-shoulders text, citing and building on the lineage of the field: Michal Zalewski (AFL), Andreas Zeller (fuzzing research), Daniel Stenberg (curl), Peter Yaworski (web hacking), and the Zero Day Initiative, with forewords from Jacob Soo and Shubham Shah.
- Local attack surface is treated as seriously as remote: named pipes, Unix domain sockets, symlink attacks, world-readable and world-writable pipes, and IPC artifacts are all mapped, a reminder that privilege escalation lives in the plumbing.
- Chapter 10 spends real pages on the market and ethics of zero days, including third parties who pay for them, then lands firmly on coordinated disclosure and using research to secure organizations, framing the offensive skill set as fundamentally defensive.
