# 53. The IDA Pro Book

**ISBN** x9780000000538  |  **Lobe** offensive

> Chris Eagle's definitive operator's manual for IDA Pro, turning a stripped binary into a navigable map through disassembly theory, FLIRT library recognition, IDC/IDAPython/SDK scripting, obfuscation defeat, and vulnerability triage; reach for it when the artifact is the binary and the wire/source has run out.

## Reach for this when

- We pull a firmware image, embedded ICS/OT binary, or vendor agent off a device and have no source or docs; the disassembler is the only authoritative read of what the code actually does (Nick's firmware/embedded specialty).
- We have a stripped static binary from an AI-infra appliance or model-server container and need to separate application logic from library noise fast; FLIRT/FLAIR signature generation is the move that collapses hundreds of unknown functions.
- We need to reverse a closed-source protocol or auth check below the HTTP layer that aimap cannot fingerprint, to write a probe or confirm a trust assumption from the binary rather than the banner.
- We are confronting packed or obfuscated code (anti-debug, disassembly desync, dynamically computed targets, import-table hiding) and need the IDA-driven static plus debugger-integration de-obfuscation loop.
- We want to scale binary analysis with scripting: IDC/IDAPython to enumerate functions, label arguments, drive cross-reference walks, or batch-triage many samples into buckets.
- We are doing after-the-fact vulnerability discovery (binary-diffing a patch to find the bug, locating ROP gadgets, mapping stack frames) on a target where only the compiled artifact exists.

## Principles

- Disassembly is a hard problem with two flawed strategies: linear sweep (decode every byte in order, fooled by data-in-code) versus recursive descent (follow control flow, blind to indirect/computed targets); IDA blends both and the analyst supplies the judgment the algorithm cannot.
- The database, not the binary, is the workspace: every name, comment, type, structure, and cross-reference you add is a stored annotation that turns raw bytes into a navigable knowledge artifact you keep refining.
- Library-code recognition is the force multiplier: FLIRT signatures (and FLAIR to mint your own from static libs) mark and rename known functions so analysis time concentrates on the application's unique code, not on re-deriving libc.
- IDA is a platform, not a tool: IDC, IDAPython, the SDK, plug-ins, loaders, and processor modules let you extend it to any file format or instruction set, so automation scales the manual craft.
- Reverse engineering and dynamic analysis converge: the disassembler maps structure statically, the integrated debugger resolves what only runs (decryption loops, anti-analysis, computed addresses), and you ride between the two views to defeat obfuscation.
