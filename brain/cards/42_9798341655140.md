# 42. From Day Zero to Zero Day

**ISBN** 9798341655140  |  **Lobe** offensive

> The zero-day discovery operating manual: model source-to-sink reachable paths and prove them with whichever of code review, reverse engineering, or fuzzing the target's visibility allows.

## Reach for this when

- You have an unfamiliar target and need a disciplined target-selection triage instead of poking randomly: run the Familiarity / Availability / Impact axes before committing research months
- You found a crash or logic flaw and need to decide if it is actually a vulnerability: use the source-to-sink reachability + security-impact test, treat confirm-exploitability as a first-class gate not an afterthought
- You confirmed one bug and want leverage: encode its root cause as a CodeQL/Semgrep AST query and sweep the rest of the repo, then thousands of other repos, for every sibling (the Expat integer-overflow variant-analysis play)
- You have a binary and no source: triage it by type (Electron, PyInstaller, .NET CLR, Java bytecode, native static/dynamic/stripped/packed) to pick the right unpacking and analysis path
- Manual reasoning ran out and you need mechanical exploration: stand up a fuzzer and pick its axes (black/gray/white box, generate vs mutate, input type, feedback loop) for the target at hand
- A fuzzer stalls on a checksum or validation gate: diagnose the fuzz blocker, patch the check or write a harness past it, and steer with coverage
- You have a working finding and need to close the loop: structure the vuln report (summary, deterministic repro, root cause, remediation) and run coordinated disclosure through the right CNA or ZDI

## Principles

- Source-to-sink is the spine: a vulnerability is a reachable, attacker-influenced path from where untrusted input enters (source) to a dangerous operation (sink); every technique is a different way to find or prove that path
- The three disciplines are complementary lenses on the same path, not rival schools: code review reads it from source, reverse engineering reconstructs it without source, fuzzing finds it by mechanical exploration; mastery is fluid hand-off between them
- Bugs are not vulnerabilities until reachable from attacker-controlled input with security impact; exploitability confirmation is a gate, not a footnote
- One bug implies many: the leverage is in variant analysis, encoding the root-cause pattern and sweeping it across one codebase and across the ecosystem
- Without source you build a gray box: coverage, dynamic instrumentation (Frida), emulation (Qiling/Unicorn), and symbolic execution progressively recover the visibility source would have given, so the work is steered not blind
- Coverage is the currency of fuzzing and the work is unfinished until reported: coverage-guided beats dumb, and vulnerability research is ultimately a defensive act closed by coordinated disclosure

## Moves

- Sink-to-source taint walk: start at a dangerous function, work backward to test whether attacker-controlled input reaches it, filter for genuinely exploitable scenarios, then build a minimal PoC
- Automated variant analysis: model a known bug as an AST query in CodeQL or Semgrep, run it across the origin repo, then scale the same pattern across many repos to harvest every sibling of the bug class
- Attack-surface mapping by taxonomy: enumerate web client, web server and nontraditional web endpoints, network protocols, and local surfaces (Unix domain sockets, named pipes, symlinks, world-readable/writable pipes, IPC); read the relevant technical standard as the map of parsers and trust boundaries
- Binary triage by type before analysis: classify Electron / PyInstaller / .NET CLR / Java bytecode / native (static, dynamic, stripped, packed) because each demands a different unpack-and-analyze path
- Static-plus-dynamic RE: disassemble and decompile in Ghidra and dump strings for static leads, then strace/ltrace library and syscalls, hook with Frida, and plant canary strings to confirm which inputs reach which code at runtime
- Hybrid analysis to steer: collect and visualize code coverage, emulate firmware and isolated functions with Qiling/Unicorn (hijack API calls, bind virtual paths), and apply symbolic execution with custom SimProcedures to solve input constraints
- Graded fuzzing ladder: black-box protocol fuzzing with boofuzz, zero-setup mutation fuzzing with radamsa, binary-template fuzzing with FormatFuzzer/010 Editor templates, crash triage with AddressSanitizer
- Coverage-guided depth with AFL++: corpus minimization, harness writing, diagnose and remove fuzz blockers (checksums, validation gates), patch checks to reach guarded code
- Language/grammar-aware fuzzing: Jazzer for Java, native Go fuzzing, dictionary- and grammar-based fuzzing for structured text, and OSS-Fuzz infrastructure for scale
- Disclosure craft: structure the report (summary, deterministic reproduction, root cause, recommendations) and run coordinated disclosure via CVE/CNA or the Zero Day Initiative

## Watch out

- The companion full-read trips a cyber-content safeguard, so this card is synthesized from front matter, TOCs, chapter framing, and the index, not the running prose; named tool invocations are accurate as targets but exact flags and code listings must be pulled from the book or companion source, not paraphrased from here
- Patch-the-validation-check to reach guarded code (fuzz-blocker removal) is a binary-modification technique; on engagement targets that means working on your own copy, never a production binary, and re-verifying the original is exploitable unmodified before claiming a finding
- Variant-analysis cross-repo sweeps generate candidates, not findings; a CodeQL/Semgrep hit is a lead that still needs the source-to-sink reachability and exploitability gate, same load-bearing verification stage the NuClide methodology insists on, do not report query hits as bugs
- Book scope is software product zero-days through coordinated disclosure; it is not a substitute for OT/ICS consequence modeling or for the deployed-system, deadline-bound pentest mode (see #30) - know which discipline the engagement is actually asking for
- Coordinated-disclosure and zero-day-market material is descriptive; under NuClide protocol disclosure recipient resolution and any disclosure recommendation are explicitly out of default scope and only run when Nick asks by name
