# 39. Agentic Architectural Patterns

**ISBN** 9781806029570  |  **Lobe** ai-agentic

> The blue-team blueprint for agentic AI - 40-plus named patterns, three maturity models, and a worked ADK/CrewAI/LangGraph loan processor - which doubles as my attacker's map of where agent trust boundaries, tool gates, and human-in-the-loop guardrails actually sit (or are missing).

## Reach for this when

- Assessing an exposed agent platform (LangGraph/CrewAI/ADK/A2A/MCP) and I need to predict its internal anatomy - reasoning engine, tool registry, memory store, orchestrator - before probing, so I know which boxes to attack.
- I find an MCP (agent-to-tools) or A2A (agent-to-agent, port/Agent-card discovery) surface and need to reason about the trust layer it implements and what an unauth read of the Agent card or tool registry yields.
- Triaging whether a deployed agent has a real Human-in-the-Loop gate or just a cosmetic one: the draft_report-vs-submit_report tool split is the exact control I look for and the exact thing operators omit.
- I need to grade an org's agentic maturity (is this an L1 monolithic POC or an L4 supervisor system with audit trails) to scope likely misconfigurations and blast radius.
- Building or fingerprinting an agent scanner and I want the canonical tool-naming, state-schema, and orchestration vocabulary (FunctionTool, AgentTool, TypedDict state, conditional edges) to match against banners and JS bundles.
- Reasoning about an agent's failure-injection surface - what happens under RESOURCE_EXHAUSTED/429, watchdog timeout, retry storms, or a network blip that makes an agent hallucinate deleted infra.

## Principles

- An agent is an engineered system with an anatomy (reasoning engine + tools + memory + planning), not a prompt. Attack the anatomy: the tool contracts and the memory store are softer than the LLM.
- Agent blast radius >> RAG blast radius. An agent acts on the world through tools, so a single instruction-drift or injection event has real-side-effect impact - this is why governance, audit trails, and the submit-tool gate are the load-bearing controls.
- Pattern-first means the controls are named and therefore enumerable: Instruction Fidelity Auditing, Persistent Instruction Anchoring, Execution Envelope Sandboxing, Agent Self-Defense, Trust Decay - their ABSENCE in a deployment is the finding.
- The agentic stack has three trust layers worth mapping separately: Function Calling (base), MCP (Anthropic, vertical, agent-to-tools), A2A (Google, horizontal, agent-to-agent, now Linux Foundation, pitched as 'SMTP for AI agents'). Each is a distinct attack surface with its own discovery primitive.
- Multi-agent orchestration passes JSON between specialists; the orchestrator is a semantic data mapper forwarding fields like customer_id. That inter-agent JSON contract (Pydantic-or-not) is an injection and confused-deputy boundary.
- Maturity is observable from outside: a self-improving MLOps L3 system looks different on the wire than a monolithic POC. Mis-aligned maturity ('architectural overreach') is where the misconfigurations cluster.

## Moves

- Map the target agent to the Sense-Reason-Plan-Act-Memory anatomy first; enumerate the tool registry and memory backend (vector store / managed memory bank) as separate assets - the memory store is often an unauth vector DB, which routes straight to aimap.
- Hunt the missing Human-in-the-Loop gate: confirm whether a high-stakes action tool (submit, provision, transfer) is exposed directly or gated behind a draft-only tool + human approval. Direct exposure on an irreversible action = critical-class finding.
- Fingerprint the framework from artifacts: ADK (LlmAgent, FunctionTool, AgentTool, BuiltInPlanner, ThinkingConfig, InMemorySessionService, gemini-3-flash), CrewAI (role/goal/backstory Agents, Process.hierarchical, manager_agent, kickoff), LangGraph (TypedDict state, node functions, conditional edges, compile/stream). Build aimap probe configs from these tokens.
- Probe the MCP and A2A surfaces as discovery primitives: an A2A Agent server exposes an Agent card describing capabilities; reading it unauth enumerates the agent's tool surface and downstream reach without exercising it.
- Inject failure to map robustness gaps: trigger 429/RESOURCE_EXHAUSTED, time out a tool, or simulate a transient network blip and watch for the IT-remediation-agent failure mode (hallucinating deleted infra, trying to provision an expensive cluster) - the absence of Adaptive Retry + Self-Correction is demonstrable.
- Pull the instruction contract: if ThinkingConfig(include_thoughts=True) or equivalent observability is on, the agent's internal monologue and IC-Fingerprint (e.g. 'LOAN-FCoT-v3-Delta0710') leak the system's reasoning, thresholds, and policy logic - read it, do not just note it.
- Grade maturity against the three models (GenAI L0-L6, Agentic Spectrum L1-L6, Implementation L1-L3) to scope the engagement: L1-L2 deployments lack the audit/sandbox/auth patterns that L3+ adds.

## Watch out

- This is a build-it book, not an attack-it book. Every 'pattern' is a defender's ideal; in the wild, half are absent. Do not assume a deployed agent has the controls the book prescribes - the gap IS the assessment.
- Heavy vendor specificity dates fast: gemini-3-flash, ADK/CrewAI/LangGraph APIs, thinking_budget=1024, the ~20-requests/day free-tier cap. The durable content is the patterns and trust layers; treat version strings as expiring fingerprints, not facts.
- The ROI and maturity framing is enterprise-sales-flavored ($0.50 agent vs $12 human, $45k/month saved). Useful for CISO impact translation, useless as a security claim - never cite it as evidence.
- FCoT, STEPScore, R5, the IC-Fingerprint are the authors' coined constructs, not industry standards; recognize them as branding when fingerprinting their specific framework, but do not expect them on arbitrary targets.
- The book equates 'has a pattern' with 'is safe.' A submit_report gate, an Execution Envelope, or an auth pattern can be present and bypassable - verify the control actually holds, do not credit it on presence. This is the verification-is-load-bearing rule applied to agent controls.
