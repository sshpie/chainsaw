# 33. Chaos Engineering

**ISBN** 9781492043850  |  **Lobe** defensive

> The discipline of running falsifiable production experiments to confirm a control actually fires under turbulence; the load-bearing-verification doctrine for "does the defense work" instead of "does the defense exist".

## Reach for this when

- A scan says a control IS present and I need to prove it FIRES. The ChaoSlingr finding is the whole methodology in one fact: a firewall caught a misconfigured port only HALF the time, and a cloud config tool caught it every time but logged it where the security team could not see it. Surface-present is not the finding; control-fires-under-turbulence is.
- I want to convert NuClide 'verification is the load-bearing stage' from a slogan into an experimental protocol: define steady state as a business-level metric, hypothesize it holds under an injected failure, try to DISPROVE it, minimize blast radius.
- Designing a security game day or a controlled red-signal exercise on in-scope infra (continuous feedback loop, not point-in-time Red/Purple teaming) and need the Generatr/Slingr/Trackr pattern plus Before/During/After facilitation.
- Assessing cyber-physical / ICS / OT or autonomous targets where you cannot just retry later. Aschbacher's rule: attack TIMING constraints first because 'by then you might be literally on fire or underwater', and map FMEA risk-priority numbers to chaos experiments that validate or invalidate them.
- I need to argue to a CISO that adding redundancy, removing complexity, or running lean can REDUCE safety (Challenger O-ring normalization, slack-absorbs-shock), and that resilience lives in the sociotechnical system above and below the line, not in the code.
- Building continuous-verification tooling (VisorRoam-class sensors) and need the conceptual frame: CV as the step after CI/CD, ChAP as the worked example, steady-state canary-vs-control comparison.

## Principles

- Experimentation is not testing. Testing asserts a binary outcome you already understand (validation); a chaos experiment seeks NEW information about a system you cannot fully model (verification). NuClide verification-stage work is experimentation, not assertion: a scanner produces candidates, the experiment produces the finding.
- Steady state is a business-level metric, never an internal one. Netflix uses SPS (stream/video starts per second) deliberately over system internals. For assessment: pick the signal the operator actually cares about losing, hypothesize it survives the injected failure, look to break the hypothesis.
- Minimize blast radius is doctrine, not courtesy. Granular targeting, canary control-vs-experiment clusters, an automatic abort ('big red button'), run outside active incidents. This IS the NuClide restraint ethic operationalized: confirm severity with a minimal signal, do not tip the system over.
- Resilience is sociotechnical. 'Tools don't create resilience. People do.' Above the line (people, funding, decisions) plus below the line (tools, architecture). Maps to Rasmussen's Dynamic Safety Model: a system rides a rubber band toward the safety boundary bounded by Economics, Workload, Safety; the job is to make that boundary VISIBLE.
- Intuitive safety beliefs are often inverted: redundancy can normalize primary-component failure (Challenger), removing complexity can remove safety functionality, and efficiency makes systems brittle because slack absorbs shock. Distrust 'we have a backup' the same way you distrust a default. Corollary (Dekker): 'root cause is simply the place where you stop looking any further' - PingCAP's 20 MILLION unit tests and 100% coverage still missed a production-only page-cache corruption bug.
- The experiment-selection problem is real: combinatorial failure space defeats brute force. Random kill (Chaos Monkey) is the entry point, observability-driven expert intuition is better, Lineage-Driven Fault Injection (reason backward from good outcomes to minimal fault sets via SAT/ILP) is the principled answer.

## Moves

- Run the loop on any control you are assessing: (1) define a measurable steady-state output, (2) hypothesize it holds under an injected real-world variable (instance kill, latency, dependency failure, resource exhaustion, network partition), (3) inject on a minimized blast radius, (4) try to DISPROVE. A 200-with-data that survives the injection is a verified control; a deviation is the finding.
- Apply the ChaoSlingr Security Chaos Engineering pattern to a control test: Generatr injects the bad state (e.g., a misconfigured port), Slingr fires it, Trackr records whether the control detected AND logged it WHERE the responders look. The two failure modes to hunt are 'caught only sometimes' and 'caught but logged where nobody sees it'.
- For cyber-physical / ICS / OT and autonomous targets: enumerate timing constraints first and attack those, because physical processes cannot retry. Take an existing FMEA, treat each risk-priority number as a hypothesis, and run a chaos experiment to validate or invalidate it. Account for the probe effect with dummy probes, formally bounded probes, or always-on built-in probing.
- Map the four TiDB fault-injection categories onto any target as an injection menu: application (SIGKILL/SIGSTOP/renice), CPU+memory (busy loops, cgroups), network (tc latency/reorder, iptables, proxies, physically unplug), filesystem (FUSE fault hooks). Use Prometheus-style steady-state metrics (QPS, P99/P95) as the comparison signal.
- Run a Before/During/After game day with a facilitator: cognitive interview to capture work-as-done, explicit scope and anti-goals (Slack Disasterpiece Theater), management buy-in, hypothesis and roles ('Creating Foresight'), run, debrief. Use it to distill and SHARE expertise across a team, not just to find one bug.
- Score the exercise with the Kirkpatrick Model (Reaction, Learning, Transfer, Results) and separate direct ROI (incident avoided) from collateral ROI (the broken assumptions you surfaced). Place the org on the Chaos Maturity Model: Adoption (how much of the org plus management buy-in) by Sophistication (manual/scoped up to automated/continuous/production).

## Watch out

- Published April 2020. ChAP, ChaoSlingr, Schrodinger, Vizceral are dated; the book itself notes Chaos Mesh was already open-sourced by press time. Use the DOCTRINE, not the named tooling; pair with a current hands-on chaos toolkit for any practicum.
- Deliberately light on hands-on labs. This is a manifesto and human-factors text, not a copy-paste lab manual. Its value is the experimentation-vs-testing distinction, safety science, and org-maturity model, not runnable commands.
- 'Run in production' is a core principle for THEIR own systems under THEIR ownership. On engagement targets that is an irreversible action: minimize blast radius is non-negotiable, and a production-impacting experiment always returns to Nick for explicit go. Do not inject faults into a client's live system as if it were your Netflix.
- Do not conflate it with antifragility. The authors explicitly REJECT Taleb: chaos experiments surface EXISTING weaknesses and build confidence, they do not make a system thrive on disorder. Stressors are not making the system stronger; you are measuring a boundary.
- Steady-state-metric framing assumes you can observe a clean business-level signal. On a black-box external target you often cannot read SPS-equivalent internals, so the loop degrades to inference; be honest that this is 'surface open, experiment not exercised' rather than a verified resilience claim.
- Most case studies are large-org SRE (Netflix, Google, Slack, Capital One). The maturity model and ROI math assume staffing and buy-in a solo researcher or a small target lacks; translate scale-down before quoting their numbers as norms.
