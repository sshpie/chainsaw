# 23. Windows 7 Resource Kit

**ISBN** 9780735638952  |  **Lobe** craft-code

> The vendor's own engineers documenting every Windows endpoint trust boundary and the assumption each defense makes - reach for it to know where a control fails, not just that it exists.

## Reach for this when

- Assessing a Windows endpoint and you need the canonical map of trust boundaries: MIC integrity levels, per-service SIDs, the TPM/PCR seal, UAC token split, AppLocker rule classes - to reason about where each one fails rather than scanning for CVEs.
- Doing privilege-escalation work on Windows and you need to model UAC internals (two-token split, manifest levels, virtualization-to-VirtualStore, auto-elevation heuristics) and AppLocker bypass surface (path rules over publisher rules) from the source.
- Modeling disk-encryption attacks and you need the BitLocker key hierarchy worked example (FVEK/VMK, TPM/PCR seal, BCD MAC tamper-evidence) plus the failure modes the book itself flags - cold-boot, DMA, TPM-less USB-key mode.
- Building a sandbox or capability-scope for an autonomous agent and you want a proven analog: per-service least-privilege with a policy the actor cannot relax, audit-only-before-enforce, deliberate refusal of a silent-elevate shortcut.
- Communicating endpoint risk to a CISO and you need the reusable preventive / detective / reactive countermeasure scaffold and defense-in-depth layer-mapping language.
- Reasoning about a Windows worm or service-exploit chain and you need to know exactly what Windows Service Hardening sandboxes (NetworkService/LocalService) versus what it leaves omnipotent (LocalSystem).

## Principles

- Defense-in-depth is the organizing logic, not a chapter: each malware vector (bundling/social-eng, browser exploit, network worm, physical theft) is mapped to four independent layers so single-layer failure or human misconfig does not yield compromise. Find the layer the operator drifted off.
- Least privilege by default inverts the old 'everything runs as admin' assumption: even an admin gets a standard-user token at logon, full token only after consent on the secure desktop. The trust boundary moved; attacks move with it.
- There is no 'authorize once' bypass on purpose (Margosis): a silent-elevate mark would migrate the whole ecosystem to silent elevate and re-create the malware problem. Read this as a design pattern - any capability shortcut you add to an agent gets universally abused.
- Security degrades over time through operational drift (a tech disables a setting mid-troubleshoot, a mobile box misses updates), so the durable posture is centralized policy that re-asserts itself, not one-time hardening. Assessment corollary: the gap is usually drift, not absence.
- Verification is a first-class countermeasure: Code Integrity is detective, UAC/AppLocker write specific Event IDs (4648/4624/4688, TokenElevationTypeFull), every preventive control is paired with detective and reactive ones. Mirrors the  verify-is-load-bearing thesis.
- 64-bit is structurally more secure than 32-bit because three protections become mandatory there - PatchGuard, hardware DEP, kernel-driver signing - so target the 32-bit hosts first.

## Moves

- UAC enumeration: read the app manifest requested-execution level (asInvoker / highestAvailable / requireAdministrator), check for filename auto-elevation heuristics (install/setup/update), and inspect VirtualStore redirects (%LocalAppData%\VirtualStore for legacy writes to %ProgramFiles%/%WinDir%/HKLM\Software) as a foothold-and-persistence surface.
- UAC elevation auditing: enable Audit Process Tracking + Audit Privilege Use, filter Security log for Event ID 4688 and search TokenElevationTypeFull (type 2 is the only type that prompts; 1 default, 3 limited); 4648 precedes 4624 with Consent.exe in path.
- BitLocker recon and decommission: manage-bde -status; recovery via repair-bde from WinRE; secure key destruction via WMI Win32_EncryptableVolume.GetKeyProtectors / DeleteKeyProtector then Win32_TPM.Clear. Recovery password is exactly 48 digits entered with F1-F10. Default cipher 128-bit AES+Diffuser; FVE driver Fvevol.sys.
- Service SID hardening inspection: sc qsidtype <svc> and sc sidtype <svc> restricted|unrestricted|none; sc qtriggerinfo <svc> for firewall triggers. SID format S-1-5-80-{SHA1 of short service name}. LocalSystem services are unprotected by WSH - prioritize them.
- AppLocker bypass reasoning: default rules allow Windows folder + Program Files + admins by path; any user-writable path under those defeats path rules. Publisher rules survive updates (allow Office signed, version >= 12.0.0.0). Always note whether the deployment ran Audit Only before Enforce.
- Firewall stealth fingerprinting check: Windows 7 suppresses outbound TCP RST and replies ICMPv4 type3/code3 (port unreach), code2 (proto unreach), ICMPv6 type1 - so a closed port and a firewalled-but-listening port look identical to a scanner. Account for it before calling a port closed.
- IE Protected Mode / MIC mapping: IE runs Low-integrity, writes only to Temporary Internet Files\Low; escalation goes through IEUser.exe (User Broker) and IEInstal.exe (Admin Broker). A browser compromise cannot silently plant a startup item - find the broker abuse instead.
- DirectAccess perimeter mapping: UDP 3544 (Teredo), IPv4 proto 41 (6to4), TCP 443 (IP-HTTPS); IPv6-Internet adds ICMPv6, UDP 500, IPv4 proto 50 - the always-on-corpnet-over-IPv6 model is an always-present remote-management surface on mobile fleets.

## Watch out

- Dated to 2009 / Windows 7. Not a current-threat reference. UAC, AppLocker, and BitLocker have all evolved (later AppLocker bypasses, BitLocker without-TPM and DMA attacks, the Windows 7 end-of-life). Use it for the reasoning pattern and trust-boundary model, not for current control efficacy.
- It is the vendor's own narrative: 'secure by default' is the engineers' framing. Read every 'this defeats X' claim as the designer's intended assumption, which is exactly the seam to attack. The book tells you what the control assumes - it does not red-team itself, you do.
- Marketing numbers like the 3Sharp SmartScreen study (caught ~9 of 10 phishing sites, 0 false positives on 500 good sites) are vendor-favorable benchmarks, not independent results - do not cite as efficacy evidence.
- The 'security via manageability' DirectAccess argument cuts both ways: an always-on-corpnet-over-IPv6 mobile fleet is also an always-present remote attack and lateral-movement surface, not purely a defensive win.
- Defense-in-depth language can lull into assuming layers are independent when in practice an operator who disables one control (drift) often disabled several; do not assume the other layers held just because the book says they are independent.
