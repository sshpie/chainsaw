# 08. The Art of Readable Code

**ISBN** 9781449318482  |  **Lobe** craft-code

> The line-level readability rulebook: one metric (minimize time-till-understanding) and a dense kit of naming, comment, control-flow, and subproblem-extraction moves you reach for whenever you or an agent are writing code another reader must verify.

## Reach for this when

- Writing or refactoring a NuClide single-binary tool (aimap, recongraph, tiptoe, BARE, the garlic scripts) and you want the craft standard - minimal deps, elegant chaining, clean output - to be concrete instead of vibes
- Reviewing LLM-agent-generated code where speed of human verification is the bottleneck (the agentic-coding lobe produces code at scale; this is the rubric that makes it auditable)
- A variable carries a trust/unit state (untrusted input, plaintext secret, _ms, hex_id) and you need the name itself to stop a mishandling bug before it happens
- A function or block does more than one thing and the reader has to hold too much at once - time to list tasks and extract subproblems
- You catch yourself about to write 20 lines of parsing when a Unix one-liner (awk | egrep | sort | uniq -c | sort -nr) or an existing library does it
- Writing test code for a tool and tests are unreadable enough that nobody will add more

## Principles

- The Fundamental Theorem of Readability: minimize the time it takes someone ELSE to understand the code, where understand = can change it, find bugs, see its interactions. All other rules are subordinate. Fewer lines is good; less time-till-understanding is better - a one-line clever expression can read slower than two plain lines.
- A name is a tiny comment. Encode danger and units exactly where a bug could sneak in: untrustedUrl, plaintext_password, hex_id, _ms. Use the limit/range vocabulary (max_/min_ inclusive, first/last inclusive, begin/end inclusive-exclusive, is/has/can booleans, no negated terms). Devil's-advocate every name: what else could a reader read into this?
- Match user expectations: get() and size() are assumed cheap. A heavy getMean() should be computeMean(). list::size() being O(n) silently made a ShrinkList O(n^2) that passed all unit tests and took over an hour on a million elements - the canonical lesson that a name shaped a real perf bug.
- Comments capture what the writer knew that the code cannot show: director commentary (the 40%-faster-binary-tree note), the story behind a constant (NUM_THREADS=8, image_quality=0.72), flaws via TODO/FIXME/HACK/XXX, anticipated Huh? questions. Never write a crutch comment for a bad name - fix the name.
- Minimize mental baggage in control flow: changing value left / stable value right in comparisons, positive-simple-interesting case first, guard clauses and early return/continue to flatten nesting, avoid ternary/do-while/upward-goto. Break giant expressions with explaining and summary variables (Cowan: humans hold only 3-4 things at once). Treat variables as cost - fewer, smaller scope, write-once/const.
- Extract unrelated subproblems aggressively (most code is generic), do one task at a time, describe the solution in plain English first (rubber-ducking) then match code to the words. The most readable code is no code at all: question requirements to a simpler problem (Texas-only locator drops Earth curvature; one-item cache beats a 100-line LRU), reuse libraries, delete dead code.

## Moves

- Trust-state-in-name pass: grep a tool's source for variables holding network input, secrets, or unvalidated data and rename to carry the state (untrusted_, plaintext_, raw_, sanitized_). Makes mishandling visible at the assignment site - the defensive-coding habit that prevents implicit-trust bugs.
- Task-listing refactor: before splitting a fat function, write the numbered list of tasks it does (e.g. parse vote_value, format location first_half/second_half, UpdateCounts three regions), then carve each into its own region or function so the reader thinks about one thing at a time.
- Extract-unrelated-subproblem sweep: for each line ask 'does this serve the high-level goal or solve a generic side-problem?' Pull side-problems (spherical_distance, ReadFileToString, make_url_friendly) into self-contained, testable util/ functions; wrap ugly interfaces (get_cookie/set_cookie/delete_cookie).
- Negate-the-problem when logic balloons: when a function sprouts many cases (the Range.OverlapsWith [0,2)/[2,4) saga), compute the opposite (doesn't-overlap) and invert - the case explosion is the signal a simpler form exists. Apply De Morgan's: distribute the not, switch and/or.
- Plain-English-first (rubber-ducking): write the algorithm as English sentences before code; the nouns and verbs you choose reveal the subproblems to extract, and inability to describe it cleanly means something is still undefined.
- Clockless-class pattern (Ch15): pass time_t now as an argument instead of calling the clock internally, so the class is deterministic and unit-testable - directly applicable to any NuClide tool with time-bucketed counters or rate logic.
- Less-code triage before building: question the requirement (is the full LRU needed or does a one-item cache get 90%?), check if a library or a Unix pipeline already does it (15-min API read habit), and only then write code - 'avg engineer ships ~10 lines/day' is the cost argument for reuse.

## Watch out

- Deliberately line-level. It is silent on architecture, concurrency, distributed systems, threat modeling, and AI itself. It is the always-on baseline for how artifacts read, not a substitute for the heavier engineering or security texts - do not reach here for design decisions.
- Dated 2011 and Google-internal in origin; examples are C++/JS/Python idioms (kConstantName, member_) that may not map to Go (the language most NuClide tools are in). Take the principle, not the literal convention.
- 'Readability does not conflict with efficiency/architecture/testability' is asserted, not proven, and the synthesis itself admits the smaller-is-better rule has exceptions (the hash-fast comment that adds code). Treat the no-conflict claim as a default, not a law - the O(n) size() bug shows readability and performance can diverge.
- Aggressive subproblem extraction has a stated failure mode: do not over-extract. Splitting into too many tiny functions trades nesting for jump-chasing and can raise reader-time, the opposite of the goal.
- The principles reduce reader-time but do not catch logic errors - the Range.OverlapsWith code was readable and still wrong twice. Readability aids verification; it is not verification. Keep the load-bearing test/verify stage.
