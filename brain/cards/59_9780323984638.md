> The CUDA canon: how to map a problem onto SMs, warps, and the memory hierarchy so a kernel is bound by arithmetic, not DRAM bandwidth, taught through nine reusable parallel patterns and six application case studies.

## Reach for this when

- You need to decide whether a GPU kernel is memory-bound or compute-bound and by how much: compute the compute-to-global-memory-access ratio (OP/B) and place it on the Roofline against A100 peaks (1555 GB/s, 19,500 GFLOPS FP32, 156,000 GFLOPS tensor).
- You are hand-writing a CUDA kernel and want to lift it off the performance cliff by reasoning about occupancy (2048 threads/SM, 65,536 registers/SM, 164 KB shared/SM), memory coalescing, control divergence, and shared-memory tiling.
- You are accelerating one of the nine covered patterns (convolution, stencil, histogram, reduction, scan, merge, sort, SpMV, BFS) and want the known-good parallelization plus its data-layout tradeoffs.
- You are choosing a sparse-matrix or graph storage format (COO vs CSR vs ELL vs hybrid ELL-COO vs JDS vs CSC) and need the compaction-vs-regularization tradeoff for coalescing and load balance.
- You are implementing the compute substrate under a neural net (convolution layer, GEMM via im2col, cuDNN) and need to know what the framework is actually running on the SMs.
- You are parallelizing a loop-heavy scientific application and must pick scatter vs gather decomposition to kill atomic contention (MRI FHD reconstruction, electrostatic potential DCS).
- You are scaling across multiple GPUs or an HPC cluster and need CUDA streams plus pinned memory to overlap compute with MPI communication, or dynamic parallelism for irregular/recursive work.

## Principles

- Arithmetic intensity governs everything. The compute-to-global-memory-access ratio (OP/B) sets the ceiling: naive matmul is 0.25 FLOP/B and SpMV is ~0.25 (no reuse), both memory-bound; 16x16 tiling lifts matmul to 4 OP/B (~6220 GFLOPS on A100). The Roofline Model tells you whether to chase bandwidth or FLOPS.
- The hardware runs 32-thread warps in lockstep (SPMD, not SIMD per Flynn 1972). Control divergence inside a warp serializes the taken paths; uncoalesced access wastes DRAM bursts. Coalescing means consecutive threads touch consecutive addresses via i = blockIdx.x*blockDim.x + threadIdx.x.
- Occupancy is a resource budget. Each SM caps at 2048 resident threads, 65,536 registers (A100: 32 regs/thread for full occupancy), and 164 KB shared memory; register spilling and over-allocation trigger the performance cliff. cudaGetDeviceProperties reads the real limits.
- Latency is hidden by parallelism, not avoided. Zero-overhead warp scheduling swaps stalled warps for ready ones, so keep enough warps resident that the SM never idles on a global-memory or __syncthreads() stall.
- Six-optimization checklist (Table 6.1): maximize occupancy, coalesce global access, minimize control divergence, tile for reuse, privatize atomics, coarsen threads. Thread coarsening amortizes redundant work (binary searches in merge, exclusive scans in radix sort) across more elements per thread.
- Scatter vs gather is the decomposition fork. Input-centric scatter forces atomics and contention; output-centric gather lets each thread own its output in a register. Loop fission plus loop interchange convert scatter into gather (MRI FHD, DCS).
- Work efficiency vs step efficiency is a genuine tradeoff. Kogge-Stone scan is O(N log2 N) work but fewer steps; Brent-Kung is O(N) work (2N-2-log2N ops) but ~2x steps. Radix sort beats O(N log N) but only for lexicographic keys; merge sort stays general.
- Compaction costs regularity. Every sparse/graph format trades space for accessibility, coalescing, and load balance; the winning format is data-dependent (nonzero distribution or vertex-degree spread decides), which is why SpMV sustains only a fraction of dense FLOPS.

## Moves

- Tiled matmul: cooperatively load TILE_WIDTH x TILE_WIDTH tiles into __shared__ with __syncthreads() between phases (strip-mining); 16x16 tile yields 4 OP/B. In production call cuBLAS or CUTLASS GEMM instead.
- Constant memory for read-only broadcast: __constant__ (64 KB) filled by cudaMemcpyToSymbol; ideal when all threads in a warp read the same index (convolution filter bank, MRI k-space). Store x/y/z as an array-of-structs so all three land in one constant-cache line.
- Convolution: tiled kernel with ghost/halo cells leaning on the L2 cache for halo reuse (9.57 OP/B for 5x5 filter, 32x32 tile). Stencil: register tiling with inPrev/inCurr/inNext planes and z-coarsening to cut the 58% halo overhead of an 8x8x8 tile.
- Histogram: atomicAdd into a per-block privatized histogram in shared memory, then merge to global; choose contiguous vs interleaved input partitioning; add aggregation for high-collision streams.
- Reduction: convergent reduction tree (log2(N) steps) that keeps active threads contiguous to minimize control and memory divergence; segmented multiblock finish with atomicAdd; a coarsening loop before the tree.
- Scan: Kogge-Stone with double-buffering to defeat the write-after-read race; Brent-Kung reduction plus distribution trees for work efficiency; hierarchical segmented scan for arbitrary length; single-pass domino/stream scan with adjacent-block sync via __threadfence() and dynamic block-index assignment. Or Thrust.
- Merge: co-rank function (binary search, O(log N)) to find each thread's input ranges, tiled with circular buffers to reuse all shared-loaded data, coarsened to amortize the search cost.
- Radix sort: 1-bit-per-pass, destination index from an exclusive scan of the extracted bit; local sort in shared memory then coalesced global write; larger r-bit radix cuts passes (2^r buckets) but hurts coalescing; LSD vs MSD strategy.
- Sparse/graph: SpMV/CSR (thread-per-row, no atomics) vs SpMV/ELL (padded, transposed column-major, coalesced) vs hybrid ELL-COO vs JDS (sort rows by length to cut divergence). BFS: vertex-centric push (CSR)/pull (CSC)/direction-optimized, frontiers with privatized block queues, atomicCAS for idempotent level labeling.
- Deep learning + scaling: convolution layer as GEMM via im2col unrolling (expansion ratio ~K*K), or cuDNN with lazy on-chip im2col (Winograd/FFT/GEMM algos). Multi-GPU: CUDA streams + cudaHostAlloc pinned memory + cudaMemcpyAsync to overlap MPI_Sendrecv; unified memory via cudaMallocManaged with page faulting; dynamic parallelism child-grid launch (set cudaLimitDevRuntimePendingLaunchCount) for Bezier/quadtree recursion; __sin()/__cos() SFU intrinsics when accuracy allows.

## Watch out

- The numbers are Ampere/A100-specific (108 SMs, 6912 cores, 2048 threads/SM, 65,536 regs/SM, 164 KB shared, 1555 GB/s, 19,500 GFLOPS). Hopper/Blackwell and consumer parts differ; re-read limits with cudaGetDeviceProperties, never hardcode.
- It is a CUDA/NVIDIA book. Almost nothing transfers verbatim to AMD ROCm/HIP, Intel oneAPI, Metal, or portable SYCL/OpenCL, though the patterns and the arithmetic-intensity reasoning do.
- Most kernels are pedagogical, not production. The text says outright to call cuBLAS, CUTLASS, cuDNN, and Thrust rather than hand-roll GEMM, convolution, scan, or sort. The value is understanding, not copy-paste.
- Best format is data-dependent for sparse/graph work. There is no single winner; the nonzero distribution or vertex-degree spread decides, so benchmark on your real dataset rather than picking from the page.
- The advanced-features chapter (Ch22) is a moving target: unified memory, page-fault migration, cooperative kernels, and pending-launch limits evolve every CUDA release; verify against the current CUDA C++ Programming Guide before relying on a capability.
- No security content. This is a performance-engineering text; the side-channel, supply-chain, and GPU-tenancy attack angles are ours to add through the chained security books, not in here.
