# 35. Cloud Penetration Testing

**ISBN** 9781803248486  |  **Lobe** offensive

> The legal-and-scope on-ramp for testing AWS/Azure/GCP from the provider's own Cloud Shell: shared-responsibility scoping, provider rules-of-engagement, and the cross-cloud tool roster (Prowler, Pacu, ScoutSuite, Trivy) you reach for before going deep.

## Reach for this when

- A target moves from on-prem/embedded into AWS, Azure, or GCP and I need the scope-and-legality frame first: who owns what under shared responsibility, and which provider policy (AWS pentest policy, Microsoft Cloud Pentest RoE, GCP AUP) legally trumps the client contract
- I need the universal first-pass cross-cloud scanner reach: 'prowler aws | azure | gcp' with CSV/JSON/HTML out, before reaching for any provider-specific framework
- Assessing exposed object storage on a cloud target - GCPBucketBrute for GCS, BlobHunter/CloudBrute for Azure, Cred Scanner/CloudFrunt/Buckethead for AWS - the auth-on-default thesis tested at the bucket layer
- Containerized workload in scope (ECS/EKS/ACI/AKS/Cloud Run/GKE): need the LoadBalancer-as-attack-vector frame and the Trivy / kube-bench / kube-hunter / kdigger scan roster
- I have to write the deliverable for executives and need the EPSS-before-CVSS triage order, the fixed report section structure, and the dollar-risk framing (cite IBM Cost of a Data Breach)
- Quick orientation on a cloud provider's first-party security stack (Security Hub/GuardDuty/Inspector/Macie, Defender for Cloud/Sentinel, Security Command Center/Cloud IDS/Cloud DLP) as a free starting signal source

## Principles

- Shared responsibility defines where scope actually lives: provider secures OF the cloud (hardware, datacenter, its code), org secures IN the cloud (your code, traffic, config). The IaaS/PaaS/SaaS gradient is just 'how much of the code is yours' - it tells you which layer is even testable
- The provider's rules of engagement legally override the client's wishes because you are testing on someone else's infrastructure; never contract for anything the AWS/Microsoft/GCP policies forbid. If unsure it is permitted, do not do it
- EPSS first, then CVSS: a CVSS 9.5 / EPSS 5% vuln ranks below a CVSS 5.7 / EPSS 95% one because EPSS estimates real-world exploitation probability. Sort the report by EPSS, then CVSS
- A pentest is distinguished from a crime solely by written, mutually signed consent with a specific scope (IPs, segments, domains) you never exceed; a handshake agreement does not hold in court, and even a bare vuln scan without it is risky
- Internal attacks are easier and more destructive than external because the adversary skips the break-in and proceeds via privilege escalation and lateral movement; only zero-trust (re-auth at every point, trust nothing by origin) meaningfully detects them
- Misconfiguration is an exploitable vulnerability, demonstrated concretely: even a near-empty GCP lab leaked a public bucket (storage.objects.list/get) and a default Cloud Run image scanned 'very misconfigured'

## Moves

- Run the cloud from the provider's browser Cloud Shell, treating the laptop as a thin client (quad-core, 4 GB RAM is enough - the cloud does the compute); spin free-tier labs in all three clouds and watch billing to stay at zero
- Cross-cloud first pass: 'prowler aws' / 'prowler azure' / 'prowler gcp' (-h to enumerate checks, output CSV/JSON/HTML); then provider-specific - Pacu modules + Cred Scanner/CloudFrunt/Redboto/WeirdAAL/awspx on AWS; MicroBurst/PowerZure/ScoutSuite/SkyArk/MFASweep on Azure; GCPBucketBrute + GCP Scanner on GCP
- Object-storage sweep: 'python3 gcpbucketbrute.py -k <keyword> -u' for unauthenticated GCS enumeration + privesc checks; GCP Scanner 'scanner.py -o <dir> -ls -m' to enumerate what a credential set can reach including GCE instance-metadata creds
- Container workflow: deploy via Cloud Run/ECS/ACI + GKE/EKS/AKS, expose with 'kubectl expose deployment ... --type LoadBalancer --port 80 --target-port 8080', inspect with 'kubectl get pods/get service', then scan with 'trivy image --image-config-scanners config <image>' and 'trivy k8s -n kube-system --report summary all --timeout 1500s'; supplement with kube-bench (CIS), kube-hunter, kdigger
- Triage for the report: resolve unknown scores at CVEDetails.com, sort findings EPSS-then-CVSS, write each vuln's exploitability in your own words, split CVE-mapped findings from non-CVE 'Other Findings' (e.g. accounts lacking MFA), map observed behavior to MITRE ATT&CK (six lateral-movement techniques, data-from-cloud-storage)
- Use the first-party stack as a free signal source before/alongside third-party tools: Security Hub aggregates IAM/Macie/Inspector/GuardDuty/Firewall Manager/Config; Inspector and SCC emit CVE/CVSS-tagged findings you can lift straight into the deliverable
- Engagement discipline: signed contract with specific scope before any activity (even a scan), re-read the provider pentest policy each engagement, never DDoS-simulate except the narrow AWS-only carve-out (under 20 Gbps, under 5M pps on CloudFront / 50,000 pps elsewhere, not from another AWS resource, terminable anytime)

## Watch out

- Beginner, breadth-over-depth by design: it explicitly says you need no YAML/JSON and build no tools. For an adversary-emulation operator it is an orientation and tool-roster card, not a technique source - it has no IAM privesc chaining, no exploit dev, no real adversary emulation depth
- Hard version/UI rot: Trivy v0.44.1, specific console click-paths, and tool flags will date fast. Treat the tool names as durable, the exact invocations and console steps as stale-on-arrival - verify against current docs
- The 'run native first-party scanner findings into the report' move conflicts with verification discipline: Security Hub / Inspector / SCC emit candidates, not confirmed findings. A CVE-tagged output is a lead to verify with a 200-with-data read, never an asserted finding
- The shared-responsibility line ('Amazon secures the cloud') can lull you into treating the provider layer as out of scope - but provider-side misconfig the customer controls (public buckets, over-broad IAM, exposed metadata) is exactly where the findings live; the model scopes the contract, it does not bound the attack surface
- The DDoS carve-out is an AWS-only, tightly-bounded exception, not a general license; Azure and GCP forbid it. Do not generalize the 20 Gbps / 5M pps numbers across providers
- 'Kubernetes is a fork of Docker' is a pedagogical simplification that is technically wrong (different projects, different scope); use the control-plane breakdown (etcd, apiserver, scheduler, controller-manager) which is sound, ignore the lineage claim
