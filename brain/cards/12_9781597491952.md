# 12. Open Source Fuzzing Tools

**ISBN** 9781597491952  |  **Lobe** offensive

> The fuzzing-as-discipline reference: a fuzzer that does not preserve protocol integrity and verify reach is just sending the wrong checksum forever; reach for it whenever you generate malformed input or need to reason about whether an automated probe actually touched the attack surface.

## Reach for this when

- Building any input-mutation tool against a binary protocol, file format, or network service and you need the six-building-blocks checklist so your fuzzer is not just spraying random bytes at a checksum gate
- You ran a generator/scanner and it found nothing for a long time and you need the diagnostic frame: is the target rejecting everything at the first validation gate (wrong checksum, dropped session, magic-byte mismatch) so deep code is never reached
- You need to argue ROI for an automated-testing or autonomous-assessment capability to management (the 83-hour manual-cost math, the no-false-positives argument, the buy/build/borrow matrix)
- Reverse engineering an unknown binary file format and you need the diff-the-encodings HEX-editor method to find headers and field boundaries before automating
- You want the durable vocabulary to classify any automated bug-finder: generation vs mutation, smart vs dumb, value vs protocol manipulation, statement/branch/path coverage, attack surface vs total code
- You are reasoning about coverage-guided or LLM-guided autonomous test generation and want the historical anchor (EFS genetic algorithms, STP SAT-solver static input generation) for where it plateaus

## Principles

- Verification is the load-bearing stage, not generation: a fuzzer differs from another only by its ability to cause the crash, and a server that silently logs you out, enforces checksums, or caps packet size means you only ever test the input-validation gate, never deep code
- Pure random is the 1/2^32 problem: a 27-byte DNS query is 256^27 (~1e65) combinations, effectively infinite, so a real fuzzer must preserve protocol integrity (recompute checksums and lengths, respect magic bytes, drive a state machine) while it mutates
- Fuzzing has essentially no false positives: a triggered error may not be exploitable but something genuinely bad happened to the code (at minimum a DoS), which is why the ROI holds and why 'if you don't know whether it's exploitable, just fix it'
- Executed is not fuzzed: code coverage tells you whether you reached the code, not whether you stressed it (mySafeCpy shows 100% coverage with the strcpy hole hidden), and only the attack surface is reachable so 100% is neither achievable nor the target
- Bugs arrive in bunches because a developer repeats the same mistake; each pass that fixes prior bugs opens new code paths, so bug count decays near-exponentially and one run is never enough (the 100,000-clean-iterations shipping gate)
- Fuzzing is a backstop in an SDL, not a panacea: it reliably misses logical flaws, design flaws, stateful bugs, second-order injection, and brand-new vulnerability classes that need human logic

## Moves

- Apply the six building blocks before writing a single mutation: valid data set, per-byte meaning, integrity maintenance (recompute checksum/length), repeatability via fixed random seed, malformed-value arsenal, state machine. Skip one and the run silently no-ops
- Load the malformed-value arsenal by category: buffer strings (A x N, << x N), integer boundaries in literal AND encoded form (-2,-1,0,254,255,256,4094,4095,4096), format strings (%s %x %n), NULL handling, Unicode, off-by-one length bounds
- Run the three-pass balanced sweep: quick run (expected values only) -> probable run -> full quick-run (everything allowed), to balance comprehensive against complete without exploding the combination space
- Coverage-driven loop on source: gcc -fprofile-arcs -ftest-coverage, then gcov/lcov/genhtml, read the HTML for untaken branches, trace back to which input bytes gate them, mutate that field. This is the Freeciv move: sweeping byte 3 through 0-255 tripled coverage 5.4% -> 15.6% and exposed the heap overflow in receive_packet_player_attribute_chunk_100
- Closed-source coverage via PaiMei PAIMEIpstalker: IDA Pro pida_dump.py -> PIDA file, breakpoint per basic block, stalk, export hits to MySQL, re-import as a colored IDC overlay to see reached vs cold code
- Reverse an unknown file format by saving the same content in multiple encodings, diffing in a HEX editor or WinMerge to find headers (Notepad fffe/feff/efbbbf), building a template, then automating; separate parsing (load to memory) from rendering (act on data) and test both
- Use the IDOR/auth-bypass monitor trick: seed other users' data with a marker (e.g. !!! prefix), then have the fuzzer's monitor scan HTTP responses for the marker to catch parameter-tampering disclosure
- Apply the 80/20 'fuzz what counts first' ordering: send most-likely-to-crash combinations before exhaustively walking the space, then distribute the remainder
- Triage the 'found nothing' state first as a plumbing failure, not a clean target: confirm checksums recompute, the session survives, and packets are not size-clamped before concluding the target is robust

## Watch out

- The tool catalog (Ch4 frameworks, Ch5 commercial products, most file fuzzers) is 2007-stale and largely dead. Read 12 for durable methodology and historical baseline, not for what to install; route tool selection to 30, 43, 44, 42
- Commercial-vendor chapters (Ch5, parts of Ch7/Ch8 written from the vendor perspective) carry marketing framing; mine them for the technique (auto-learn, RFC-module exhaustion, generated Perl repro scripts, endpoint vs pass-through) not the product pitch
- 'No false positives' is a claim about reproducible crashes, not about exploitability; a triggered error proves something bad happened, it does not prove RCE. Do not let the slogan inflate a DoS into a critical finding without separate exploitability work
- 100,000-clean-iterations and the 20-25% (up to 75% in parsers) bug-find rates are Microsoft-SDL-era figures, not universal constants; treat them as historical reference points, not modern coverage targets
- Code coverage is a necessary diagnostic but a deceptive metric: chasing 100% wastes effort because only attack surface is reachable, and high coverage can coexist with an un-stressed vulnerability (the mySafeCpy lesson)
